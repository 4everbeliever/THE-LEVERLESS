### Phase 3: Lead Database Programmer & Optimization Defense (5 Minutes)

*(Visual Cue: Switch to SQL Editor displaying `0003_schema_expansion_and_audit.sql` and `BENCHMARKS.md`)*

#### **Speaker 2 (Lead Database Programmer & Query Optimization Engineer):**
> *"Thank you. Under Section III.2, the course strictly enforces **Automation over Application**. Our business logic does not rely on fragile client-side computation. All calculations, concurrency controls, and state transitions are executed server-side inside PostgreSQL.*

#### 1. Complex Stored Procedures & Atomic Transactions
*(Action: Highlight `public.create_booking` in `supabase/migrations/0003_schema_expansion_and_audit.sql`)*
> *"Our primary transaction engine is `public.create_booking(p_item_id, p_start_at, p_end_at, p_extras)`:*
> - *First, it validates caller authenticity server-side using `auth.uid()`, completely ignoring any client-provided identity parameters.*
> - *Second, it performs **server-side currency calculation**: duration is derived from epoch differential `ceil(extract(epoch from (p_end_at - p_start_at)) / 86400)`, multiplying by `daily_price`.*
> - *Third, it executes child insertions into `booking_items` and `booking_extras` in a single atomic transaction block. If any step fails, the entire transaction rolls back cleanly."*

#### 2. High-Concurrency Double-Booking Prevention (GiST Exclusion Constraint)
*(Action: Highlight constraint `prevent_overlapping_bookings` in SQL editor)*
> *"In logistics, standard unique constraints cannot handle time ranges. We solved this with a **PostgreSQL GiST (Generalized Search Tree) exclusion constraint** backed by the `btree_gist` extension:*
> ```sql
> ALTER TABLE public.bookings ADD CONSTRAINT prevent_overlapping_bookings
>   EXCLUDE USING gist (
>     item_id WITH =,
>     tstzrange(start_at, end_at, '[)') WITH &&
>   ) WHERE (status in ('reserved', 'checked_out'));
> ```
> *If two customers attempt to reserve the same tool for overlapping timestamps at the exact same millisecond, the database engine uses bounding-box intersection mathematics (`&&`) to reject the second transaction with error code `23P01`. Our stored function catches this violation and raises a clean client error."*

#### 3. Automated Operational Audit Triggers
*(Action: Open `public.log_table_audit()` and query `public.audit_logs`)*
> *"Per Section III.2, application-level audit logging is non-compliant. We implemented the `log_table_audit()` trigger function attached to `bookings`, `items`, and `payments`.*
> - *On every `INSERT`, `UPDATE`, or `DELETE`, the trigger executes `AFTER` the mutation.*
> - *It automatically serializes `to_jsonb(OLD)` and `to_jsonb(NEW)`, stamps the executing database user, records caller IP, and stores an immutable record into `public.audit_logs`."*

#### 4. Query Optimization & EXPLAIN ANALYZE Benchmarks
*(Action: Open `BENCHMARKS.md` on screen)*
> *"In Section V (Weeks 6 & 7 Optimization), we benchmarked critical query paths using `EXPLAIN ANALYZE`:*
> - *We engineered partial composite B-tree indexes, such as `idx_bookings_active` on `(item_id, start_at, end_at)` and `idx_items_branch_status` on `(branch_id, status)`.*
> - *Our benchmark reports prove that item availability lookups transformed from full sequential table scans into **Index Only Scans**, reducing execution time from **14.2 milliseconds to 0.082 milliseconds**—a 99.4% performance gain.*
>

### Scenario D: SQL Injection & Session ID Security Defense (Professor's Warning)
> **Instructor:** *"Notes from our syllabus: The system can't be SQL injected, and Session IDs can't be stolen or bypassed. Prove this in your system."*

#### **Spoken Answer by Speaker 3 (Frontend / Security Connector):**
> *"We have implemented a dual-barrier defense against both vulnerabilities:*
>
> #### 1. SQL Injection Immunity
> *(Action: Open `src/hooks/useInventory.ts` and the SQL migrations)*
> - *First, all API queries in our data layer use PostgREST prepared statements with parameterized registers (`$1, $2`). Client strings are never concatenated into raw SQL.*
> - *Second, in all database stored procedures, every variable is statically typed. There are **zero dynamic `EXECUTE` commands with string concatenation** anywhere in our SQL code.*
> - *Even if an attacker submits `'; DROP TABLE items; --` in our search box or form inputs, PostgreSQL binds it as a literal string to match against column data. It is never interpreted as executable syntax.*
>
> #### 2. Session ID Stealing & Bypass Immunity
> *(Action: Open `index.html` line 10 and `0001b_profiles_fixes.sql` lines 61-90)*
> - *First, **Session Bypass is impossible** because our server routines do not trust client-supplied user IDs. In `create_booking`, customer identity is derived strictly from `auth.uid()` verified via HMAC-SHA256 asymmetric cryptographic JWT signatures.*
> - *Second, **Session Stealing via XSS is blocked**: React 19 auto-escapes all JSX expressions with zero instances of `dangerouslySetInnerHTML`. Furthermore, in `index.html`, our **Content Security Policy (CSP)** strictly restricts `connect-src` exclusively to our verified Supabase host (`ophgpdwzoeuheshcfrrc.supabase.co`). Even if an unauthorized script were injected, the browser blocks exfiltrating tokens to any external server.*
> - *Third, our authentication infrastructure enforces **Single-Use Refresh Token Rotation (RTR)**. Any replay attempt of an expired token instantly revokes the entire token family, immediately locking out unauthorized sessions.*
> - *Fourth, database trigger `public.protect_role_change()` prevents users from elevating their own role to admin, halting unauthorized privilege escalation at the database engine level."*
